# Developer Experience

Score how easily a new contributor can become productive and how pleasant daily development is.

Before scoring, re-read `00-rubric.md` for severity definitions and score anchors.

> **Book sources**: *The Pragmatic Programmer* (Hunt & Thomas) for broken windows, tracer bullets, knowledge portfolio, and good-enough software.

Adjust expectations based on the project profile from Step 1: a solo prototype needs less process than a team-maintained product.

## Diagnostic Questions

### X1: Time to first meaningful change

Simulate a new developer's first 30 minutes:

1. Can they clone and install without errors?
2. Can they run the project?
3. Can they run the tests?
4. Can they make a trivial change and see it reflected?

(Hunt & Thomas: "Use tracer bullets — build something that works end-to-end early to validate direction. Tracer bullets are production-intended scaffolding. Prototypes are disposable experiments to learn about feasibility. Know the difference.")

- No `.env.example`: P2 (guess-and-check with env vars)
- No setup script, manual steps not documented: P2
- README does not mention how to run tests: P2
- Build fails with warnings that obscure real errors: P1

### X2: Are broken windows being repaired?

(Hunt & Thomas: "Do not live with broken windows. One broken window — a bad design, a poor piece of code, a failed test — starts the slide toward decay. People feel less personal responsibility for a building that looks abandoned.")

- Are there obviously broken things being ignored (failing tests, dead links in README, build warnings)?
- Is there code with "this is a hack" or "TODO: fix this" that has been there for months?
- Is there a failing test in CI that everyone has learned to ignore?
- Is there a "we will clean this up later" area that has become a dumping ground?

Each unrepaired broken window is P2. Multiple broken windows signal cultural decay.

### X3: Is "good enough" being distinguished from "perfect"?

(Hunt & Thomas: "Know when to stop. Good-enough software does not mean sloppy or badly-designed. It means accepting that some features are not perfect and shipping anyway.")

- Is the project over-engineered for its current stage (full CI/CD for a prototype, 90% test coverage for a throwaway script)?
- Is it under-engineered for its intended audience (no auth for a public API, no error handling for a paid service)?
- Does the README communicate the project's maturity level clearly?

### X4: Is tooling automated or manual?

- Is there a formatter (Prettier, Black, gofmt, rustfmt)? Enforced in CI?
- Is there a linter (ESLint, Ruff, Clippy)? Does it catch real issues?
- Are there pre-commit hooks?
- Does the tooling config live in the repo, or is it tribal knowledge?
- Is there a `Makefile` or `justfile` that wraps common commands (`make lint`, `make test`, `make build`)?

No linter or formatter at all: P1 (code quality will drift).

### X5: Does CI enforce quality?

- Does CI run on every PR?
- Does CI run: lint + type check + tests + build?
- Are failing checks blocking merges?
- Is there a build artifact verification step?

No CI at all: tag `@root:no-ci` (P1).

### X6: Is documentation an asset or a liability?

- Does the README match reality?
- Are public APIs documented?
- Are there examples showing how to use the project?
- Is there an architecture diagram or module map?
- When was the last documentation update relative to the last code change?

Stale docs are worse than no docs (they actively mislead): P2.

### X7: Is the knowledge portfolio being invested in?

(Hunt & Thomas: "Invest regularly in your knowledge portfolio. Learn at least one new language every year. Read technical books. Participate in local user groups.")

- Is there a `CONTRIBUTING.md` or onboarding guide?
- Are architectural decisions documented (ADRs, design docs, README architecture section)?
- Are dependencies kept reasonably up to date?
- Is there a changelog?
- Are there design discussions or decision records?

### X8: Is estimation honest?

(Hunt & Thomas: "Estimate to avoid surprises. Iterate the estimate with the code.")

- Are there TODO items with no time estimates?
- Are there milestones or deadlines documented?
- Is there evidence of scope creep (features added without removing others)?

P3: estimation quality is hard to assess from code alone, but the absence of any project tracking is a signal.

### X9: Is the git history navigable?

- Are commit messages descriptive, or a stream of "fix", "update", "wip"?
- Is there a meaningful `.gitignore`?
- Are there large binary files or build artifacts committed?
- Is there a branch naming convention or PR template?

## Cross-Dimension Hooks

- If no CI exists → tag `@root:no-ci`
- If no tests exist → tag `@root:no-tests` (DX suffers because developers fear breaking things)
- If broken windows are present → note this in Code Quality (dead code, stale comments)
- If the project is over/under-engineered → note this in the report's executive summary
